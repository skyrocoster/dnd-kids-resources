**Purpose:** Identify gaps in the [2026-09-24 review](README.md) and turn its findings into bounded next actions. This is a source/documentation check, not a new runtime or live-data audit. No database operation or test was run for this follow-up. The earlier review's principal reset, pagination, and documentation-drift observations remain useful; the issues below qualify or extend them rather than replacing them.

## Issues to address in the review

In particular, the review's >100-row fixture and the browser's first-page calls establish a likely completeness problem but not a count for the live campaign database ([pagination evidence](backend-and-data.md#cross-layer-pagination-risk--static-observation-not-a-confirmed-defect)).

## Ordered next actions

1. **Decide the reset/restore contract before changing scripts.** Agree which tables and state are preserved, whether a selected `--force` replaces only its group, whether `revealed_cells`/`at_the_table` are imported or deliberately excluded, and whether any failed delete, missing/malformed input, or population error must leave the old data intact. Keep the live campaign database and original seed exports untouched. Then implement and verify on a **disposable SQLite database and copied seed inputs**: repeat initialization, selected force, missing/malformed files, an injected delete/populate error, and restoration of the two state tables. Check table contents and failure reporting, not just exit codes. Do not run the present force-seeder against campaign data. See the [original safety finding](findings-and-next-actions.md#1-establish-safe-database-reset-and-restore-behavior).
2. **Prove the browser and player-spell contracts separately.** With a controlled >100-row catalog, decide whether the spell/monster browsers should fetch all pages or display explicit pagination; test selection/search beyond page one and beyond the 500-row API cap where relevant. With an assigned spell whose `quick_rules` and `alternate_description` are non-null, compare catalog JSON with **GET player spells, PUT replacement response, and GET player detail**, then make only the approved query/client changes and add focused assertions. Existing default-valued fixtures and mocked E2E routes are insufficient proof. See the [original contract finding](findings-and-next-actions.md#2-verify-the-list-and-nested-player-spell-contracts).
3. **Correct the two operational guides as a documentation-only task.** Align `frontend/README.md` with the actual port, backend startup/reuse behavior, and the split between mocked browser routes and the live health call. Reconcile `docs/FULL_TEST_PROCESS.md` with the runner's 18-check inventory and its warning exceptions; explain that `test:api` owns a temporary backend and that E2E can use an existing or short-lived backend. Determine the supported clean-install sequence before documenting root versus frontend Playwright dependencies. Do not run the aggregate runner or change package manifests merely to update prose.
4. **Assign independent owners for remaining unknowns.** Establish the intended deployment/access boundary before making the unauthenticated API reachable outside the local setup; separately identify seed provenance/redistribution and OpenAPI snapshot-refresh owners. The [review's ownership finding](findings-and-next-actions.md#3-resolve-data-contract-and-deployment-ownership) records the evidence and unknowns. Defer performance benchmarking, placeholder removal, and polling refactors until a specific need and behavior contract are agreed.

**Scope boundary:** This document proposes follow-up, not authorization to reset, export, migrate, expose services, or change application behavior. Preserve the original review and unrelated work; use focused, finite verification when an action is approved.
