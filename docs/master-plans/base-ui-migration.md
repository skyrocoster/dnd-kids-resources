# Base UI and Shared Interaction Migration

> **Status:** non-DnD interaction dispositions complete for the reviewed current production inventory; optional DND-EVALUATION remains unselected and separately approval-gated

## Destination

Cover the production frontend with a deliberate choice for each interaction: reuse Base UI-backed shared controls, retain justified native or specialized behavior, or identify a genuine gap for a component-level decision. Reduce generic hand-built interaction code without a blanket visual redesign or changes to feature rules.

## Settled direction

- The user approved the A-style audit approach, this record's location, and the six-slice envelope below—not every component disposition or implementation. The [grilling record](../grilling-docs/2026-09-23-base-ui-full-migration.md) contains the proposed matches, explicit component preferences, exceptions, and approval history. Its reported 140-module TSX audit is a planning baseline, not proof of exhaustive behavior coverage. The [shared-primitives review](../shared-primitives-review.md) remains read-only source evidence.
- Preserve layout, public value contracts, form behavior, domain rules, and intentional dismissal/focus ownership. Adopt fitting primitive keyboard and accessibility behavior rather than preserving known omissions (for example, missing menu keyboard navigation or incomplete tab semantics). Document those changes in the selected component scope; resolve conflicts rather than silently changing feature behavior.
- Reuse existing shared components first. Add or adapt generic shared APIs only for a demonstrated gap; keep justified native controls and use adapters rather than mass-changing caller contracts. A retained component is a valid migration disposition, not unfinished work.
- Keep map drawing/geometry and gestures, Loom placement and lane rules, encounter HP/status rules, responsive SplitPane behavior, and FloatingWindow drag/resize logic specialized. Shared controls may surround these interactions, not replace their domain behavior.
- Base UI and the existing calendar dependency are already in use; no **new** dependency is selected or needed for the identified overlay/field/menu work. `@dnd-kit` is only an optional evaluation candidate. Any adoption or drag-system replacement requires separate approval.
- This record does not authorize implementation, package installation, integration, or redesign. A substantial later redesign follows basic HTML → current production Storybook → explicit user approval → integration assessment. That sequence is not required for unchanged interactions or behavioral primitive substitutions.
- Keep the current CombatantCard Set HP dismissal and invalid-input behavior. Any proposed change to those rules requires an explicit component-level user decision.

## Recommended planning order and acceptance boundaries

This is a recommended sequence, not slice selection or a requirement to finish every foundation before any consumer.

1. **Confirm the proposed dispositions and select a bounded outcome.** Start from the existing audit; inspect only the selected components, their callers and relevant shared APIs. Confirm the full proposed disposition list before implementation planning, asking only about genuine exceptions—not repeating settled A-style preferences. A slice may need several focused Plans; do not turn a cross-feature label into one large change.
2. **Establish the required shared contract first.** Within FOUNDATION, treat Popover, field/checkbox and legacy Dialog as separate acceptance boundaries. Define controlled state, value/event mapping, labels, focus and dismissal ownership before consumers depend on them. Prove existing callers still work; the compound Dialog API and pending-confirmation guard must not regress.
3. **Prove one bounded consumer before expanding.** ConditionPicker is a proposed first Popover consumer because its existing behavior is documented. LoomRail can independently exercise the existing Menu. Follow with Set HP and MapLab only after their distinct close rules and Escape ownership are explicit. These are recommendations, not selected work.
4. **Expand by interaction family and feature boundary.** FORMS and DISCLOSURES can proceed independently where adapters already fit. Include ACTIONS opportunistically in each selected surface, with one owner per edit; use a separate ACTIONS Plan only for remaining ordinary controls. Existing shared field/Dialog changes belong to FOUNDATION; feature-specific migration and proof belong to their consumer Plan.
5. **Keep optional DnD research off the critical path.** Its report must address cross-lane insertion, bank/restore, activation/drag guards, pointer and keyboard interaction, and server order parity. An inconclusive or negative recommendation is a valid result; evaluation is not adoption.

Each focused Plan must name its exact consumer scope, retained behavior, intentional accessibility changes, exclusions, and finite proof. Relevant proof includes:

- **Overlays:** allowed and blocked close paths, trigger/focus return, keyboard operation, nested overlay behavior where present, and MapLab's ordered Escape handling. Set HP retains Apply/Enter/retoggle-only closing and existing invalid-input handling unless explicitly changed.
- **Fields/forms:** controlled values and callback shape, labels/errors, disabled state, empty/invalid/intermediate numeric input, staged selection and submit behavior. Preserve selected conditions absent from the available list and LootBundleEditor quantities.
- **Disclosure/choice controls:** independent and persisted expansion, exclusive selection, and keyboard behavior. Tabs require associated panels; navigation and static markers retain their actual semantics.
- **Actions:** unchanged action callbacks, disabled/pending state, accessible names and form button type; no accidental drag or navigation changes.

Use focused existing tests or bounded browser scenarios, including representative callers when a shared API changes. Carry forward unresolved exceptions explicitly; do not claim migration coverage from the historical module count or require a fresh whole-source audit for every Plan.
